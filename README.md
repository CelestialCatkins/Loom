# Loom
Loom：一个“空”的 App，和你的无限种用法

你下载到的，是一个空壳

打开 Loom，你不会看到任何现成的功能。没有计算器，没有记事本，没有待办清单。

它只做一件事：装载你给它的插件。

所有功能，都由插件提供。你可以装别人做好的，也可以自己写一段脚本丢进去。Loom 本身不预设你能做什么——它只负责把这些零件装配起来、跑起来、管起来。

就像一台没有预装任何软件的电脑。装什么，你说了算。

---

插件分两种，玩法不一样

一种是“装现成的”：别人做好的插件包，导入即用。适合复杂界面、需要性能的功能。

另一种是“写一段脚本”：用 JavaScript 或 Lua 写几行逻辑，存进项目里，立刻生效。适合轻量自动化——比如“每天早上把某个网页的数据抓下来存进本地”，改一行代码就能热更新，不用重新打包。

两种插件可以混着用：一个现成的插件负责拍照采集，你写的小脚本负责清洗数据，再一个界面插件把结果画出来。它们互不打扰，通过 Loom 内部的“服务总线”协作。

---

每个项目，是一个独立的小世界

Loom 里没有“全局安装”这回事。所有插件都归属于项目。

一个项目就是一个文件夹，里面分两层：

· UI 层：管界面长什么样
· 逻辑层：管背后干什么活

两层强制分开存放。逻辑层不能反过来依赖界面层——这条规矩由 Loom 强制守住，防止你哪天想换个界面，发现背后的逻辑全被绑死了。

整个项目可以打包导出成一个文件，换台手机导入，插件、配置、数据原样复活。你的“功能组合”是可以带走的。

---

你能“看见”插件是怎么协作的

这是 Loom 最不一样的地方。

插件关系图：一张拓扑图，告诉你哪个插件依赖哪个插件、谁在给谁供数据。一眼看出结构，颜色区分 UI 层和逻辑层。发现“逻辑层怎么反向依赖界面了”，当场就能改。

运行链条流程图：你点了一下按钮，到底跑了哪些插件、触发了哪些事件、调用了哪些服务——完整时序图直接画出来。调试复杂组合的时候，不用靠猜。

两张图都能导出成图片或代码，贴进文档、丢进版本管理，都行。

---

图标和名字，能换，但有前提

这一点必须跟你说实话。

Android 系统不允许 App 在运行时随便换图标和桌面名称。Loom 走的是系统允许的标准路子：提前在应用里预置好几套“图标+名字”的组合，你在设置里选一套，系统切换过去。

代价是：切换时 App 会重启一下，这是系统机制，绕不过去。而且预置的组合跟 App 版本绑定，不能今天随便传张图明天就生效。

所以“上传本地图片换图标”这件事，Loom 的做法是：图片存进项目里，作为一套预置配置的一部分，跟着版本走。不是即时任意替换，但能稳定用。

把这条边界提前讲清楚，比给你一个会崩的承诺强。

---

适合谁

· 喜欢自己拼装工具，而不是接受一个“什么都有但什么都不精”的超级 App 的人
· 愿意写几行脚本解决自己重复劳动的人
· 想搞清楚“我点的这个按钮背后到底发生了什么”的人
· 需要一个可移植、可备份、可版本管理的功能组合的人

---

一句话收尾

Loom 不承诺“一个 App 解决所有问题”。

它承诺的是：给你一个运行时，功能由你自己编织。 织成什么样，你说了算。
